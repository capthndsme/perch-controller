# Collector management — design

Design for making collectors **configurable and discoverable**, managed from
the dashboard, and decoupled from the box that runs the server. Written
against the code as it stands on 2026-09-21; every constraint below cites the
file and line it comes from. Nothing here is implemented yet.

> Implemented, with the review amendments at the end. Names in the body are
> the ones of the time: the project is now **Perch**, `go-collector` is the
> Perch Network Collector (`perch-collector`: binary, OpenWrt package, UCI
> config `/etc/config/perch-collector`, environment `PERCH_COLLECTOR_*`), and
> the collector can also reach the server over a WebSocket instead of being
> polled (amendment A10, docs/collector-agent.md).

**The target shapes**

| Shape | Server | Collector | How the server reaches it today |
|---|---|---|---|
| Docker compose | private bridge network | host network, listens on the stack gateway | `COLLECTOR_URL` env (`docker-compose.yml`, `COLLECTOR_URL: http://${METRICSLITE_NET_GATEWAY:-172.28.0.1}:9800`) |
| Bare metal / pm2 | host | host, `127.0.0.1:9800` | setup wizard, or `COLLECTOR_URL` (`docker-compose.host.yml`) |
| OpenWrt router | anywhere on the LAN | the router, LAN address `:9800`, UCI-generated key | **nothing** — the admin must read `uci get metricslite-collector.main.api_key` over SSH and type an address into the wizard |

The third row is the problem this document solves, plus the fact that a server
may end up with several collectors (router + a mirror-port box).

---

## 0. Decisions at a glance

1. **Discovery is collector→server announce** (`POST /api/v1/collectors/announce`),
   not server-side scanning and not mDNS. It is the only mechanism that works
   in all three shapes, crosses L3, needs no new server dependency, and can
   carry the API key.
2. **The pollable address is always derived from the TCP source address of the
   announce**, never from a self-reported address. Over TCP an attacker cannot
   forge the source address, so this is the one free authentication primitive
   available on an unauthenticated endpoint.
3. **Adoption is explicit.** An announce can only ever create or refresh one
   `pending` row. Nothing is polled, and no key is used, until an admin clicks
   Adopt.
4. **Re-announces of an adopted collector are authenticated with that
   collector's own API key**, so a row cannot be hijacked after adoption.
5. **One additive migration** adds `instance_id`, `hostname`, `version`,
   `capture_interface`, `source`, `lifecycle`, `last_announce_at`,
   `announced_base_url`, `api_key_fingerprint`. Existing rows default to
   `source='manual'`, `lifecycle='adopted'` and keep working untouched.
6. **`COLLECTOR_URL` keeps winning for the row it owns** (`source='env'`) and
   never moves a row that a collector announced.
7. **Deleting a collector destroys its history** (13 FK cascades) — so the API
   refuses a bare delete of a collector that has history, the UI's primary
   destructive action is Disable, and a real purge is a chunked ace command.
8. The poller is **already isolated per collector**; one bug is fixed (a failing
   collector is re-dispatched every 5 s regardless of its poll interval) and one
   filter is added (never poll `pending`/`dismissed` rows).

### 1.2 The migration

`database/migrations/1779000000039_add_discovery_columns_to_collectors.ts`
(the highest existing prefix is `…0038`). Additive only — no column is
dropped, renamed or re-typed, and every new column is nullable or has a
default, so the existing single row in a live install survives untouched.
`string` + an app-level union is the house style for enum-ish columns (see
`users.role` in `…0001_add_role_to_users_table.ts:8`).

```ts
 * the row there, `lifecycle` gates what the poller is allowed to touch.

 * or COLLECTOR_URL) and is already being polled, so the defaults
 * ('manual' / 'adopted') keep it working with no data migration.

      // collector never announced — MySQL allows many NULLs in a UNIQUE.

      // 'adopted'   — in service. Polled when `enabled` is also true.
```

Sizing/index notes: `collectors` holds single digits of rows, so the indexes
are for consistency with the repo's habit of naming every index, not for
speed. `base_url` is `varchar(500)`; utf8mb4 × 500 = 2000 bytes < the 3072-byte
InnoDB key limit, same as `wifi_access_points.metrics_url`, so a plain index
works with no prefix. The existing `collectors_enabled_idx` stays.

## 2. Discovery

### 2.1 Options evaluated

**(a) Collector announces itself to the server.** The daemon gets a
`server_url`, POSTs a small identity document on start and then periodically.

- Works in all three shapes. The Docker case is the interesting one: the
  server is on a private bridge (`docker-compose.yml`, `networks.default.ipam`)
  and the collector is on the host network listening on the bridge gateway
  (`GOCOLLECTOR_LISTEN: ${METRICSLITE_NET_GATEWAY:-172.28.0.1}:9800`). The
  collector can reach the server at the *published* port, and its announce
  arrives at the server from the bridge gateway address — which is exactly the
  address the server must poll. The mechanism produces the right answer for
  free in the hardest case.
- Crosses L3: a collector in another VLAN or subnet still announces.
- Can carry the API key, which is the only mechanism here that can.
- Needs no new server dependency; an HTTP POST handler is ~120 lines.
- Cost: one new unauthenticated endpoint (section 2.4 bounds it) and a config
  key the admin must set once on the collector — which on OpenWrt is one UCI
  line in the same file they already edit, versus SSH + copy the key + type an
  address into the wizard.

**(b) Server probes candidate addresses.** Sweep the LAN for `:9800`.

- Rejected as the discovery mechanism. It cannot learn the API key, so every
  find still needs manual key entry — it solves the easy half of the problem.
  It is an active port scan from a monitoring appliance (noisy, trips IDS,
  looks exactly like what the tool is supposed to detect). It needs a target
  list the server does not have: from a Docker bridge the server has no idea
  what the LAN prefix is, and 254 hosts × a 5 s timeout is minutes per sweep.
  It cannot find a collector in another subnet.
- Kept in a targeted form only: "Test this address" already exists as the
  wizard's live probe (`app/controllers/setup_controller.ts:97`) and becomes
  `POST /api/v1/settings/collectors/probe` (section 3.5). That is scanning with
  n=1 and an admin pressing the button.

**(c) mDNS / DNS-SD** (`_metricslite-collector._tcp`).

- Rejected. Multicast does not cross the Docker bridge: the server container is
  on a separate L2 segment and nothing forwards 224.0.0.251 into it, so the
  flagship deployment cannot see a single advertisement. It also does not cross
  VLANs, needs a new Node dependency plus a raw multicast socket, and the key
  would have to travel in a TXT record broadcast to the entire segment — worse
  than a unicast POST in every respect. Worth revisiting only as a convenience
  for bare-metal installs, or in a future `metricslite discover` CLI the admin
  runs on their laptop. See Open questions.

**Chosen: (a).**

### 2.2 The endpoint

```ts
const CollectorsController = () => import('#controllers/collectors_controller')

/**
 * Collector self-announcement. INTENTIONALLY outside both `auth` and the
 * requireSetupComplete gate — a router that boots before the wizard has been
 * run must still be able to show up. Everything an announce can do is create
 * or refresh ONE `pending` row; adoption is an explicit admin action under
 * /api/v1/settings/collectors.
 */
router
  .post('/api/v1/collectors/announce', [CollectorsController, 'announce'])
  .as('collectors.announce')
```

Declared next to the setup group in `start/routes.ts` (which is outside the
gate for the same reason, see the comment at `start/routes.ts:46-51`), and
before the `/api/v1` group so registration order never lets the SPA wildcard
at `start/routes.ts:258` swallow it.

**Auth: none.** A bearer token cannot be required for the first contact
(chicken-and-egg), and the admin token cannot be on a router. The endpoint is
bounded instead — see 2.4 — and *once a collector is adopted with a key, its
announces must present that key* (2.5).

**Request**

```http
POST /api/v1/collectors/announce HTTP/1.1
Content-Type: application/json
Authorization: Bearer 7f3c9d21ab64e8f0…       # present iff the collector has a key
```
```json
{
  "instanceId": "9d4c1a0f6b2e47c8a15d3e9f7b0c2a68",
  "hostname": "OpenWrt",
  "version": "0.1.0",
  "captureInterface": "br-lan",
  "port": 9800,
  "tls": false,
  "baseUrl": "http://192.168.1.1:9800",
  "apiKey": "7f3c9d21ab64e8f0…",
  "apiKeyFingerprint": "9f86d081"
}
```

`instanceId` is required; everything else is optional except `port`. `apiKey`
is sent in the body only when the daemon is configured with
`announce_api_key: true` (default, section 6.1); the `Authorization` header
carries the same value and is what re-announce authentication checks, so a
deployment that dislikes keys in bodies can send only the header.

**Validator** — `app/validators/collectors.ts`, `vine.compile(vine.object(…))`
like `app/validators/wifi.ts:13-47`:

```ts
import vine from '@vinejs/vine'

/** Daemon-generated: 32 hex chars today; the shape is deliberately loose. */
const INSTANCE_ID_REGEX = /^[A-Za-z0-9_-]{8,64}$/
const FINGERPRINT_REGEX = /^[0-9a-f]{8}$/

export const collectorAnnounceValidator = vine.compile(
  vine.object({
    instanceId: vine.string().trim().regex(INSTANCE_ID_REGEX),
    hostname: vine.string().trim().maxLength(255).optional(),
    version: vine.string().trim().maxLength(64).optional(),
    captureInterface: vine.string().trim().maxLength(64).optional(),
    port: vine.number().min(1).max(65535),
    tls: vine.boolean().optional(),
    baseUrl: vine.string().trim().url({ require_protocol: true }).maxLength(500).optional(),
    apiKey: vine.string().trim().minLength(8).maxLength(512).optional(),
    apiKeyFingerprint: vine.string().trim().regex(FINGERPRINT_REGEX).optional(),
  })
)
```

**Response** (the standard `{ data }` envelope from
`providers/api_provider.ts:18`):

```json
{
  "data": {
    "status": "pending",
    "collectorId": 4,
    "announceIntervalSeconds": 60
  }
}
```

`status` is `pending | adopted | dismissed`. The daemon uses
`announceIntervalSeconds` to pace itself (60 s pending, 900 s adopted, 21600 s
dismissed — the server owns the schedule so it can be tuned without a
collector release).

### 2.3 The address rule

**`base_url` is always `{scheme}://{announce source address}:{announced port}`.**
`scheme` is `https` when `tls: true`, otherwise `http`. What the collector
claimed goes into `announced_base_url` for display only.

Why: a self-reported address is worthless (a collector listening on `0.0.0.0`
or `127.0.0.1` does not know how the server reaches it, and a hostile one
would happily name someone else's box), whereas a TCP source address is
something the peer had to actually possess to complete the handshake. It is
also correct in all three shapes: bare metal → `127.0.0.1`; Docker → the bridge
gateway the collector listens on; OpenWrt → the router's LAN address.

Mechanics: `request.ip()`. Adonis's default `trustProxy` trusts loopback, so
behind the Apache vhost in `docs/ops/apache-perch.conf` (`ProxyPass /
http://127.0.0.1:12553/`, mod_proxy_http adds `X-Forwarded-For`) this still
resolves to the real client. IPv6 literals are bracketed when composing the
URL. If `request.ip()` is loopback but the announce is reaching a server that
is not on the collector's host (impossible to detect reliably), the admin can
still fix the address with the update endpoint — see the caveat below.

**Caveat, documented deliberately:** if a collector sits behind a reverse proxy
or a NAT relative to the server, the source address is not the address to poll.
Such a deployment must either turn announcing off (`server_url: ""`) and add
the collector manually, or accept that an announce will rewrite `base_url` back
to the source address. Listed in Open questions.

### 2.4 What an announce may do — and the limits

| Announce matches | Server action |
|---|---|
| a row with the same `instance_id` | authenticate (2.5); refresh `hostname`, `version`, `capture_interface`, `announced_base_url`, `last_announce_at`; follow the address into `base_url` **only if `source='announced'`**; reply with that row's lifecycle |
| no `instance_id` match, but a row whose `base_url` equals the computed address **and** whose `instance_id IS NULL` | **claim**: set `instance_id`, `hostname`, `version`, `capture_interface`, `announced_base_url`, `last_announce_at`. Leave `lifecycle`, `base_url`, `api_key`, `name`, `enabled` untouched. Reply with that row's lifecycle |
| nothing matches | **create**: `lifecycle='pending'`, `source='announced'`, `enabled=false`, `name` = `hostname` or `collector-{first 6 of instanceId}`, `poll_interval_seconds=5`, key + fingerprint stored if announced. Reply `pending` |

The claim rule is what makes upgrades seamless: the row the compose stack
created from `COLLECTOR_URL`, or the row the wizard created, absorbs its
daemon's identity on the first announce instead of producing a confusing
duplicate. It only fires when the existing row has no identity yet, so it can
never steal an already-identified collector.

Hard limits, all in `app/services/collector_announce.ts`:

- **Feature switch.** `SystemSetting.get<boolean>('collector_announce_enabled')`,
  default `true` (same key/value pattern as
  `app/services/hostname_enrichment_settings.ts:3`, and togglable from the
  Collectors page). Off → `403 { "error": "announce_disabled" }` with no DB read.
- **Rate limit.** In-process token buckets (no limiter package is installed;
  `package.json` has `@adonisjs/lock` but not `@adonisjs/limiter`), keyed by
  source address: **12/minute per address, 60/minute globally**. The per-address
  map is capped at 256 entries with oldest-eviction so it cannot grow from LAN
  churn. Over → `429 { "error": "announce_rate_limited", "retryAfterSeconds": 60 }`
  plus a `Retry-After` header.
- **Pending cap.** At most **16** rows with `lifecycle='pending'`. A new
  `instance_id` beyond that → `409 { "error": "announce_pending_limit" }` and a
  `logger.warn`. Refreshes of existing pending rows still work, so a full
  pending list never blinds the admin to the collector they are waiting for.
- **No side effects beyond one row.** An announce never enables polling, never
  changes an adopted row's key, never changes a `manual`/`env` row's address,
  and never returns a secret.

### 2.5 Re-announce authentication

For an announce matching a known `instance_id`:

- **Stored key is not null** → the announce must present the same key (Bearer
  header, or `apiKey` in the body). Mismatch or absence →
  `401 { "error": "announce_key_mismatch" }`, **no writes**, `logger.warn` with
  the source address. Comparison is constant-time over the SHA-256 digests.
- **Stored key is null** (a collector with no auth configured) → accepted. There
  is no secret to check; the source-address rule is the only binding, which is
  the same guarantee an unauthenticated collector gives the poller anyway.

Consequence: after adoption, an attacker must know the collector's API key to
move or rename it. Before adoption there is nothing to protect.

### 2.6 Adopt and dismiss

**Adopt** (`POST /api/v1/settings/collectors/:id/adopt`) sets
`lifecycle='adopted'`, `enabled=true`, applies the optional `name`,
`pollIntervalSeconds` and `apiKey` overrides, runs `probeCollector` and stores
the result exactly the way the wizard does
(`app/controllers/setup_controller.ts:97-107`) so a failed probe still adopts
and is visible. From the next scheduler tick the collector is polled. Returns
`{ collector, probe }`.

If the row has an announced `api_key_fingerprint` and the admin supplies a key
with a different fingerprint, adopt returns
`422 { "error": "collector_api_key_mismatch" }` unless the body also carries
`"acceptKeyChange": true` — a typo-catcher, not a security boundary.

**Dismiss** (`POST /api/v1/settings/collectors/:id/dismiss`) sets
`lifecycle='dismissed'`, `enabled=false`, and clears `api_key` (and its
fingerprint) — we were never asked to hold that secret. The row is kept so the
collector's continued announces refresh a hidden row instead of reappearing in
the pending list; the daemon is told `dismissed` and drops to a 6-hour beat.
An admin can un-dismiss by adopting it from the "dismissed" filter, which will
ask for the key again. Both actions are idempotent per state and return
`422 { "error": "collector_not_pending" }` when applied to a row that is
already `adopted` (adopt) — dismiss is allowed from any lifecycle, since
"stop talking to this thing" must always be available.

### 2.7 Threat model (home LAN, one admin)

What someone with access to the LAN **can** do:

- Create pending rows (spam the adoption list). Bounded to 16 rows and 12
  announces/minute/address; visible; deletable; nothing is polled.
- Offer a fake identity — hostname, version, interface, a key. Harmless unless
  the admin adopts it, and adopting it only means the server polls the
  attacker's HTTP service and records fabricated traffic counters under a
  separate `collector_id`. The fingerprint shown next to the pending row is
  there so the admin can compare it with `uci get …api_key` before adopting.
- **Read a plaintext announce, if they can see the collector's traffic** (an
  unswitched segment, a mirror port, a compromised router). That reveals the
  collector's API key, which grants read access to per-device byte counters —
  a subset of what someone in that position can already derive by watching the
  packets themselves. Mitigations: an `https` `server_url`, or
  `announce_api_key false` and paste the key on adopt.

What they **cannot** do:

- Move, rename, re-key or re-point an adopted collector without knowing its API
  key (2.5) *and* being at the address they want it polled at (2.3).
- Read any key back out: `collector_transformer.ts:16` emits `hasApiKey`,

### 3.7 Delete — and what happens to history

`DELETE /api/v1/settings/collectors/:id`

**Recommendation: deleting a collector must not silently destroy its history,
and must never cascade inside an HTTP request.**

Both halves matter. All thirteen child tables are `ON DELETE CASCADE`
(section 1.1), and those tables *are* the database — the status notes record
`device_protocol_buckets` at 18 M rows and `device_traffic_buckets` at 7.6 M
(`docs/looking-glass-status.md`). A single `DELETE FROM collectors WHERE id=?`
would take InnoDB minutes inside one transaction, blocking the poller and the
dashboard, and would be issued by a UI button whose label says "Remove". The
repo already knows this shape of problem: `app/services/bucket_retention.ts:76-79`
batches deletes at 50 000 rows precisely so "each DELETE stays short".

So:

1. `DELETE …/:id` with no history (no rows in `device_traffic_buckets` for that
   `collector_id`) → deletes the row, `204`, matching `deleteWifiSource`
   (`settings_controller.ts:103-113`). This is the normal case for a mistaken
   manual entry or a dismissed announcement.
2. `DELETE …/:id` with history → `409`:
   ```json
   {
     "error": "collector_has_history",
     "message": "Collector 2 has recorded traffic. Disable it to stop polling and keep the history, or purge it with `node ace collectors:purge --id=2`.",
     "bucketRows": 7614322
   }
   ```
3. The purge is an ace command, `commands/purge_collector.ts` →
   `node ace collectors:purge --id=N [--dry-run]`, following
   `commands/prune_buckets.ts` (a `--dry-run` that only counts, a rendered
   summary table) and reusing the batched-delete helper style of
   `bucket_retention.ts:279-300`: delete from each child table in 50 000-row
   batches, then remove the `collectors` row.
4. The UI's primary destructive action is **Disable** (`enabled=false`), which
   stops polling and keeps every chart intact — `collectorId` filters in
   `app/validators/devices.ts` keep working against a disabled collector's
   history.

Rationale for keeping the FK cascades as they are: they are correct for the
purge path (the command deletes children itself, the cascade is the safety
net), and turning them into `RESTRICT` would mean thirteen ALTER TABLEs on the
largest tables in the database for no user-visible gain.

### 3.9 Coherence with the wizard and `COLLECTOR_URL`

**`POST /api/v1/setup/collector` keeps working unchanged.** It creates a row
with the new defaults (`source='manual'`, `lifecycle='adopted'`), which is

**`default_collector.ts` precedence.** Today `ensureDefaultCollector`
(`app/services/default_collector.ts:32-66`) skips when a row already has that
URL (`:39-41`), moves the row when there is exactly one (`:42-49`), and skips
as `ambiguous` when there are several (`:50-52`). With announced rows in the
table, "exactly one row" is no longer a safe proxy for "the row I own" — a
router that announced and was adopted would get yanked to the compose address.
New rule set, in order:

| Condition | Action |
|---|---|
| a row's `base_url` already equals `COLLECTOR_URL` | `skipped: 'exists'` — plus set `source='env'` on it if it was `manual`, so the next boot takes the fast path |
| a row with `source='env'` exists | update its `base_url` (+ key if given) — exact ownership, no guessing |
| exactly one row exists and its `source='manual'` | update it and mark it `source='env'` — the upgrade path for every install that exists today |
| only `announced` rows exist (any number) | **create** a new `source='env'`, `lifecycle='adopted'` row |
| several rows, none `env`, at least one `manual` | `skipped: 'ambiguous'` (unchanged) |

`ensureDefaultCollector` gains `source: 'env'` and `lifecycle: 'adopted'` on
the rows it creates, and a fourth `DefaultCollectorResult` variant is not
needed — `'created' | 'updated' | 'skipped'` still covers it.

If the compose collector is *also* given `GOCOLLECTOR_SERVER_URL`, its first
announce claims the env row by address (2.4) instead of duplicating it. The
compose file does not need to change; this is only relevant if a user adds it.

## 4. Poller isolation

### 4.1 What is already correct

`app/tasks/poll_collectors.task.ts` is a single 5-second dispatcher
(`:31-33`), loads `Collector.query().where('enabled', true)` (`:36`), filters
to the due-and-not-in-flight set (`:40-45`), and runs them through
`Promise.allSettled` with a per-collector `try/catch/finally`
(`:47-83`). `pollOnce` never throws — every failure path returns
`{ status: 'failed' }` via `persistFailure`
(`app/services/collector_poller.ts:653-656`, `:705-722`) — and every HTTP call
is bounded by a 5 s `AbortController`
(`collector_poller.ts:317-338`, `probeCollector` likewise at
`collector_probe.ts:8, 34-36`). The `inFlight` set (`poll_collectors.task.ts:12`)
stops one collector's slow cycle racing itself.

The dispatcher's own tick is also non-blocking: `@outloud/adonis-scheduler`
constructs croner without the `protect` option
(`node_modules/@outloud/adonis-scheduler/build/src/scheduler.js:147`) and
`config/scheduler.ts:17-22` enables no task lock, so a tick that runs long does
not delay or swallow the next one.

**Conclusion: an unreachable collector cannot delay another collector's poll.**
Worst case it occupies one in-flight slot for ~5 s (summary and devices are
fetched in parallel, `collector_poller.ts:365-368`) while every other collector
runs concurrently. The only shared resources are the Node event loop and the DB
pool, so a collector returning an enormous device list can still slow others
indirectly — that is a capacity question, not an isolation bug.

### 4.2 The bug: a dead collector is hammered every 5 seconds

`lastPollAtFor` (`collector_poller.ts:205-207`) reads a snapshot map that is
written **only on the success path** (`:605-609`, after the bucket writes).
`persistFailure` (`:705-722`) deliberately does not touch it. So for a collector
that is down, `lastPollAtFor` stays at its old value and the dispatcher's due
test (`poll_collectors.task.ts:40-44`) is true on **every** tick, regardless of
that collector's `poll_interval_seconds`. A collector configured at 3600 s that
is unplugged gets two connection attempts every 5 seconds, forever, each
writing `collectors.last_status` — 12 rows/minute of pointless UPDATE traffic
and 12 log lines, per dead collector.

**Fix** — in `app/services/collector_poller.ts`:

```ts
/**
 * When each collector may next be dispatched (epoch ms). Written on EVERY
 * outcome, unlike the snapshot map, so a collector that is down backs off
 * instead of being retried on every 5 s tick.
 */
const nextAttemptAt = new Map<number, number>()

/** Consecutive failures per collector; drives the backoff and last_status.failures. */
const failureCount = new Map<number, number>()

const FAILURE_BACKOFF_MS = [5_000, 10_000, 20_000, 40_000, 60_000]

export function nextAttemptAtFor(collectorId: number): number {
  return nextAttemptAt.get(collectorId) ?? 0
}
```

- On success: `failureCount.delete(id)`; `nextAttemptAt.set(id, now + pollIntervalSeconds * 1000 - 1500)`
  (the 1500 ms slack that lives at `poll_collectors.task.ts:43` today moves here).
- On failure: `n = (failureCount.get(id) ?? 0) + 1`; back off by
  `Math.max(pollIntervalSeconds * 1000, FAILURE_BACKOFF_MS[Math.min(n, 4)])`;
  write `failures: n` into `last_status` so the UI can say "down for 12 polls".
- `_resetPollerState()` (`:194-197`) clears both new maps.
- The dispatcher's filter becomes
  `!inFlight.has(c.id) && now >= nextAttemptAtFor(c.id)`.
- `lastPollAtFor` stays exported (three poller specs use `pollOnce` directly and
  the helper is part of the tested surface).

### 4.3 The filter: never poll a row that is not adopted

`poll_collectors.task.ts:36` becomes:

```ts
const collectors = await Collector.query()
  .where('enabled', true)
  .where('lifecycle', 'adopted')
```

served by `collectors_lifecycle_enabled_idx`. Announced-but-pending rows carry
`enabled=false` as well (2.4), so this is belt and braces — but the belt is
what stops a future "enable" toggle on a pending row from quietly starting a
poll against an unadopted address.

The same filter belongs in `commands/inspect_collector.ts:38` (`.where('enabled', true)`)
so the debug command matches what the poller actually does.

### 4.4 Status and `last_seen_at`, per collector

Unchanged and already correct: a successful poll sets `last_seen_at = now` and
`last_status = { ok: true, … }` (`collector_poller.ts:626-633`); a failure sets
only `last_status = { ok: false, error }` (`:710-714`), leaving `last_seen_at`
as the genuine "last time this thing answered". The additions are
`last_status.failures` (4.2) and `capture_interface` being mirrored into the new
`collectors.capture_interface` column on a successful poll, so the settings
list can show the interface even while the collector is down.

`last_announce_at` is written only by the announce path; the two timestamps
answer different questions ("it talked to us" vs "we talked to it") and a
disagreement between them is itself diagnostic — the Collectors page shows both.

### 6.2 `internal/announce` — implementation outline

```go
// Package announce tells a metricslite server that this collector exists.
// It is strictly one-way and idempotent: the server records an identity and
// an address, and an administrator decides whether to poll it.
package announce

type Options struct {
    ServerURL        string
    InstanceID       string
    APIKey           string
    SendAPIKey       bool
    Port             int
    TLS              bool
    Hostname         string
    Version          string
    CaptureInterface string
    Interval         time.Duration
    Client           *http.Client // test seam; nil = a 10 s-timeout client
}

type Announcer struct{ /* opts, status, lastErr, mu, stop chan struct{} */ }

func New(opts Options) *Announcer
func (a *Announcer) Run()            // blocking loop; started as a goroutine
func (a *Announcer) Stop()
func (a *Announcer) Status() Status  // {Server, State, LastAnnounce, LastError}
```

- **Wiring** in `main.go`: after `apiServer.ListenAndServe()` is started
  (`main.go:118-123`) and before the signal wait (`:126`), so the API is
  already answering when the admin hits Adopt and the server probes back:
  ```go
  var ann *announce.Announcer
  if cfg.ServerURL != "" {
      id, err := announce.ResolveInstanceID(cfg.InstanceID, cfg.InstanceIDFile)
      if err != nil { log.Printf("announce: %v", err) }
      ann = announce.New(announce.Options{...})
      go ann.Run()
  }
  ```
  and `ann.Stop()` in the shutdown block next to `apiServer.Shutdown()` (`:139`).
- **Instance id** — `ResolveInstanceID`: explicit config wins; else read
  `instance_id_file`; else generate 16 bytes from `crypto/rand`, hex-encode,
  `os.MkdirAll(dir, 0o755)` + write `0600`; if the write fails, fall back to
  `sha256(/etc/machine-id)[:16]`; if that fails too, use an in-memory random id
  **and log a warning that the collector will need re-adopting after a restart**.
- **Schedule** — first announce after `2–5 s` of jitter (so a router booting
  its whole network does not stampede), then a ticker. The interval comes from
  the server's `announceIntervalSeconds`, clamped to `[15 s, 6 h]`, with ±10 %
  jitter. `context`-free; a `select` on `time.After` and the stop channel.
- **Backoff** — on transport error or 5xx: `30 s → 60 → 120 → 300 → 900` cap.
  On `429`, honour `Retry-After`. On `401 announce_key_mismatch`, log loudly
  once (*"the server has a different key for this instance id"*) and drop to the
  6-hour beat — retrying cannot help.
- **TLS** — `http.Client{Timeout: 10 * time.Second}` with the default transport
  and system roots; `InsecureSkipVerify` only when `announce_tls_insecure`, and
  when it is on, log it at start so it appears in `logread`.
- **What is sent** — exactly the payload in 2.2. `baseUrl` is composed from
  `cfg.Listen` via `net.SplitHostPort`; when the host is `0.0.0.0`/`::`/empty it
  is omitted and only `port` is sent (the server uses the source address either
  way). `apiKeyFingerprint` is `hex(sha256(key))[:8]`, always sent when a key
  exists; `apiKey` only when `SendAPIKey`. The `Authorization: Bearer` header is
  always set when a key exists.
- **Logging** — one line per *state change* (`pending → adopted`), not per beat;
  never log the key or the fingerprint's source.
- **Exposure** — `Announcer.Status()` is surfaced as `meta.announce_status`
  (a plain string: `"pending"`, `"adopted"`, `"error: …"`) on the authenticated
  endpoints in `internal/api/api.go:58-62`. **Not** on `/healthz`
  (`api.go:199-201`), which is unauthenticated and should not advertise the
  server's address.

### 6.3 OpenWrt package

`openwrt/metricslite-collector/files/metricslite-collector.config` gains:

```sh
		# falls back to its own file/machine-id scheme.

	fi
	config_get server_url main server_url
	config_get announce_interval main announce_interval '60'
	config_get_bool announce_key main announce_api_key 1
	config_get_bool announce_insecure main announce_tls_insecure 0
	…
		GOCOLLECTOR_SERVER_URL="$server_url" \
		GOCOLLECTOR_ANNOUNCE_INTERVAL="$announce_interval" \
```

`openwrt/README.md` — add the three rows to the options table (`:43-53`) and a
short "Point it at the server" section:

```sh

/etc/init.d/metricslite-collector restart
```

Docker compose is **not** changed: `COLLECTOR_URL` already registers the

## 7. Security

| Concern | Control | Where |
|---|---|---|
| Keys at rest | AES via the `encryption` service, keyed by `APP_KEY`; decrypt failures return `null` rather than throwing | `app/models/collector.ts:26-40`; kept out of generated schema by `database/schema_rules.ts:11-16` |
| Keys in API responses | Transformer emits `hasApiKey` + a fingerprint, never the key; the column is `serializeAs: null` | `app/transformers/collector_transformer.ts:16`, `app/models/collector.ts:28` |
| Keys visible to non-admins | The non-admin `GET /api/v1/collectors` returns no address and no key material at all | section 5.3 |
| Keys in transit, server→collector | `Authorization: Bearer` over the LAN; `https` base URLs work today | `collector_probe.ts:40`, `collector_poller.ts:328` |
| Keys in transit, collector→server | Sent on the announce when `announce_api_key` is on. `https` `server_url` removes the exposure; `announce_api_key false` removes it at the cost of one paste | section 6.1 |
| Announce abuse | Feature switch, 12/min/address + 60/min global, 16 pending rows, adoption always manual, address derived from the TCP source, adopted rows require the key | section 2.4, 2.5 |
| Hijacking an adopted collector | Needs both the API key **and** possession of the address | section 2.3, 2.5 |
| Management surface | `auth + requirePasswordChange + requireAdmin` on the whole `settings` group | `start/routes.ts:111`, `app/middleware/require_admin_middleware.ts:14-18` |
| Server-side request forgery | The server only ever fetches an address an admin created or adopted; announces cannot make it fetch anything | section 2.4 |
| Accidental data loss | Delete refuses when history exists; purge is an explicit chunked command | section 3.7 |

Honest residual risks, stated so nobody is surprised:

1. A LAN attacker can spam 16 pending rows and 12 announces/minute. Bounded and
   visible, but it *is* an annoyance vector.
2. An announce over plain HTTP carries the collector's API key in cleartext to
   anyone who can observe that path.
3. An admin who adopts a pending row without checking the fingerprint has
   pointed the poller at whatever announced. The UI shows the fingerprint and
   the address for exactly this reason.
4. The server has no outbound allow-list: an admin can manually register any
   URL, including one on the server's own loopback. That is unchanged from
   today's wizard.

## Open questions

1. **`lifecycle` values.** The brief asked for `pending/adopted/disabled`; this
   design uses `pending/adopted/dismissed` and keeps "disabled" as
   `enabled=false`, because a dismissed collector keeps announcing and must be
   remembered, and because the same state in two columns will drift. Confirm.
2. **`source='env'`.** A third value beyond `manual`/`announced` so
   `default_collector.ts` can identify the row it owns instead of guessing from
   "there is exactly one". The alternative is folding it into `manual` and
   accepting that `COLLECTOR_URL` may move a wizard-created row. Confirm.
3. **Does `announce_api_key` default to `true`?** True is the "it just works"
   choice and means the key crosses the LAN in cleartext unless `server_url` is
   `https`. False means every adoption needs an SSH session to read the key.
   Recommendation: `true`, with the fingerprint shown in the UI and the
   trade-off stated in `openwrt/README.md`.
4. **Reverse-proxied collectors.** The source-address rule makes a collector
   behind a proxy/NAT un-announceable (the announce will keep rewriting
   `base_url`). Acceptable, or should a `base_url` override survive announces
   via an `address_locked` flag?
5. **Wizard integration.** Should the setup wizard's collector step list pending
   announcements (a new `GET /api/v1/setup/collector/candidates` behind the same
   auth as `POST setup/collector`, and `collectorId` accepted by that POST to
   adopt rather than create)? It is a real UX win for the router case — a brand
   new install would never type an address — but it is extra surface on the
   pre-setup path. Scoped out of the work packages above pending a decision.
6. **Double counting with two collectors.** The selector in FE-3 makes the
   overlap visible but does not resolve it: `/api/v1/traffic` still sums across
   collectors by default (`devices_controller.ts:504`). Options for later: a
   `primary` flag on one collector that the aggregate endpoints default to, or
   per-collector MAC ownership. Needs a product call before any code.
7. **mDNS for bare metal.** Worth adding later as a *secondary* mechanism for
   installs where the server is not containerised, or as a `metricslite
   discover` CLI the admin runs on their laptop to print announce-ready config?
8. **Announce feature switch default.** `collector_announce_enabled = true` out
   of the box. A stricter posture would default it off and have the wizard turn
   it on. Recommendation: on, given the bounds in 2.4 and that adoption is
   always manual.
9. **Collector-side push.** Nothing here lets the server *configure* a collector
   (push a poll interval, change `top_peers_count`, trigger `POST /api/v1/reset`,
   which already exists at `internal/api/api.go:83`). A two-way channel like the
   WiFi sources' SSH option (`wifi_access_points.enable_two_way_commands`) is a
   separate design. Out of scope here — flagging it so nobody assumes adoption
   implies control.

these win.

**A1. Decisions on the open questions.** 1 (lifecycle `pending/adopted/dismissed`
+ `enabled`): confirmed. 2 (`source='env'`): confirmed. 3 (`announce_api_key`
default true, fingerprint shown): confirmed. 8 (announce switch on by default):
confirmed. 4 (reverse-proxied collectors), 5 (wizard candidates), 7 (mDNS),
9 (server → collector control): deferred, out of scope. 6 (double counting

**A2. Proxies and the source-address rule.** The Docker shape publishes the
server on the host and people put a reverse proxy in front of it. Requests
that arrive through that proxy reach the container from the stack's gateway
address, so `request.ip()` must honour `X-Forwarded-For` from that address or
every announce would compute the gateway as the collector's address. BE-2
therefore makes the trusted proxy list configurable: `TRUST_PROXY` env
(`start/env.ts`, optional string, `proxy-addr` syntax such as
`loopback,172.28.0.0/24`), consumed by `config/app.ts` `http.trustProxy`
(`proxyAddr.compile(list)`); default `loopback`, which is today's behaviour.
`docker-compose.yml` sets `TRUST_PROXY: loopback,${METRICSLITE_NET_SUBNET:-172.28.0.0/24}`
for the server; `.env.example` documents it. Behind a proxy that is not on
that list the admin can still correct `base_url` by hand (3.6), and an
announce from a `manual` row never rewrites it (2.4).

**A3. Instance identity in containers.** `instance_id_file` defaults to
`/var/lib/go-collector/instance-id`; a container without a volume there would
mint a new id on every recreate and pile up pending rows. GO-2: when the file
cannot be written, derive a stable id from `sha256(machine-id + capture
interface MAC)` and log it once; document `GOCOLLECTOR_INSTANCE_ID` and the
volume as the explicit options. The compose stack does not announce (2.4,
6.3), so this only matters for hand-run containers.

**A4. Sequencing.** All backend packages (BE-1 → BE-2 → BE-3 → BE-4) are
built by one implementer in that order: the Japa suite uses a single test
database and concurrent runs would race. FE-1 + FE-2 are built in parallel by
another implementer from the contract in sections 3 and 5; any deviation the
backend implementer has to make from the documented shapes must be reported,
not silently absorbed. GO-1 → GO-2 → GO-3 start after the nDPI 5.0 port that
is in flight on the same repository (it touches `Makefile`, `README.md`,
`CONFIG.md`). Every package is followed by an independent review of the diff
against this document; findings go back to the implementer until the review
is clean.

**A5. Not in scope of this round.** FE-3, the wizard candidates endpoint,
`address_locked`, mDNS, any server → collector control.

**A3, revised after the collector-side review.** The fallback in A3 never
fired in the case it was written for: a container without a volume can
write the id file into its ephemeral layer, so the write succeeds and a
fresh id appears on every recreate. Instance id precedence is therefore:
explicit `instance_id` → an existing id file → a **derived** stable id
(`sha256("go-collector instance id|" + machine-id + "|" + capture MAC)[:32]`,
MAC alone with a one-time log line when no machine-id exists) → a random id
persisted to the file → an ephemeral random id only when there is no MAC
either. A derived id is also persisted when the path is writable, so a later
NIC change does not rename the collector; a failed persist is never an
error. Containers recreated without a volume keep their id because the host
NIC does. Also decided in that review: `403 announce_disabled` and
`409 announce_pending_limit` drop to the 6-hour beat like 401; server error
strings are capped at 120 characters before they reach logs or
`meta.announce_status`.

**A2, narrowed after the backend review.** Every trusted proxy peer can set
the source address, so the trust list must be the proxy and nothing else.
In the Docker shape only the stack gateway ever forwards (published port,
userland proxy), so the compose default is
`TRUST_PROXY: loopback,${METRICSLITE_NET_GATEWAY:-172.28.0.1}`, not the
subnet. **A6. Re-identification.** An announce whose `instance_id` is
unknown but whose computed address already belongs to a row with a
different, non-null `instance_id` is the same collector re-identified (the
recreated-daemon case): if that row is adopted and stores a key the announce
must present it (401, no write, otherwise); on accept the row takes the new
`instance_id` and refreshes like a re-announce, keeping lifecycle, name,
address, key and enabled. Following an address change never lands two rows
on one address; the move is refused and logged instead. The has-history
check for delete counts device identities as well as traffic buckets; the
purge command disables the collector first and retries on lock errors; a
row at `COLLECTOR_URL` that is pending or dismissed is adopted by the env.

**A7. NAT gateways (open question 4, decided by the end-to-end run).** On
the owner's network the gateway's fw4 NAT-reflection SNAT for the 80/443
port-forwards to the server (`reflection_src external`) rewrites every
connection routed through it to the server's 443, its own included, so its
announces reach Apache from the WAN address and the
derived `base_url` was the public IP while `announced_base_url` carried the
right LAN address. The source-address rule stays (it is the only
unforgeable input), and the escape hatch is the update endpoint: changing
the address of an `announced` row flips its `source` to `manual`, which
announces never move; they keep refreshing hostname, version, interface and
`last_announce_at`. The response carries `warnings:
["announced_address_taken_over"]` and the page explains it. No
`address_locked` column is needed. The card already shows "reached at X,
says Y" when the two differ, which is the cue to do this.

**A8. Replacing a collector: merge, not purge (2026-09-21).** Delete refuses
once a collector has history, and purge throws the history away. A hardware
replacement needs a third path: fold the old collector's history into the new
one. That is `node ace collectors:merge --from=OLD --into=NEW`
(`commands/merge_collectors.ts`, rules in `app/services/collector_merge.ts`).
One row remains with NEW's identity. The side with more history keeps its row
id, because rewriting `collector_id` on the rollup tables is a
clustered-index move per row. Key collisions follow an overlap policy:
`replace` is automatic for overlaps of 15 minutes or less, and `into` or
`sum` must be chosen explicitly beyond that. Under `replace` only
one-row-per-poll traffic buckets and the top-peer snapshot go to the target.
Protocol rows, which are per minute, and every other accumulator add up. The
merge also refuses while the server's `COLLECTOR_URL` would re-register the
retired collector or take over the merged one. Rollups are rebuilt from the
tier below wherever it is still within retention. The command refuses when
`information_schema` shows a table referencing `collectors` that its
registry does not know, so a new per-collector table has to be added there
in the same change. The first merge was done by hand on the owner's box that
morning, from `localhost` to `gateway`. A replay of its pre-merge backup
through the command matched the hand-merged live traffic data row for row.
It also showed that the hand merge had dropped the old box's share of 106
per-minute protocol rows, which was then repaired on live.

**A9. Controller first; the wizard adopts (2026-09-21, resolves open
question 5).** The owner's deployment order is the controller first, then
collectors and access points in any order. The wizard's collector step was
mandatory, so a controller installed ahead of its router could not finish
setup. Now the step is optional. `POST /api/v1/setup/collector/skip` sets
the `setup_collectors_deferred` system setting, and `setup_state` treats the
step as done when a collector is adopted or the flag is set. The step lists
pending announcers from `GET /api/v1/setup/collector/candidates`, which is
admin only, outside the setup gate, and also reports whether discovery is
on. It adopts one through `POST /api/v1/setup/collector/:id/adopt`, which
runs the same `adoptCollector` as Settings with the same errors. This uses a
separate route rather than the `collectorId` on `POST /setup/collector` that
question 5 suggested, so each payload validates on its own. The dashboard
says when no collector is adopted yet.

**A10. The collector dials in; gateway stats come with it (2026-09-21).**
A collector with `server_url` and an API key no longer waits to be polled: it
holds a WebSocket to `/api/v1/collector-agent/ws` (subprotocol
`perch-collector.v1`, its own key as the bearer plus `X-Perch-Instance-Id`)
and its first message, `collector.hello`, runs the announce match table of
section 2.4 with the upgrade's source address, so discovery, the pending list,
the discovery switch, the pending cap and adoption are unchanged. The row
records how the collector reaches the server in `collectors.transport`
(`poll` | `agent`); the poll task skips `agent` rows, and the server pushes the
schedule (`agent.configure`, 0 while pending or disabled) so adopting,
disabling or editing takes effect at once. Pushes (`collector.push`) carry the
summary and device table a poll would fetch and go through the same ingest,
serialised per collector with polls, so a switch from poll to socket never
counts twice. A socket collector's HTTP API may answer on loopback only, so
`base_url` became nullable. Adopting a socket row without a key binds the key
the connected collector presented (never keyless), and a key that no longer
matches the live session closes it (4001); dismiss closes it with 4003. The
same change moved the Gateway page onto the collector on the router, which
reports conntrack, TCP, load, memory and WAN counters with its traffic, and
removed the node_exporter scrape (`ROUTER_METRICS_URL`). Contract:
docs/collector-agent.md.
